====================
InfoHub 规则引擎
====================

在条目审核前插入一组有序规则：自动打标签、加减评分、指派学科、直接发布或拒绝。用来
对付信息过载——把噪声压掉，把真正关心的内容顶上来。

与核心审核的分工（ADR-009）
===========================

审核状态机与人工标黑在**核心**，因为 portal 的记录规则依赖 ``item.state``，核心不能
依赖一个可选模块才能保证访问控制正确。本模块只提供规则求值，通过覆盖
``infohub.item._moderate()`` 介入::

    def _moderate(self):
        remaining = self.env["infohub.rule"]._apply(self)
        return super(InfohubItem, remaining)._moderate()

``super`` 的这个写法是关键：只对**未被规则终结**的子集调用父实现。写成
``super()._moderate()`` 会把已经被 reject 的条目也一起发布掉。

``_apply`` 返回"还需要核心决定状态"的条目，这是与核心解耦的接口——本模块只负责
"哪些条目已经定了状态"。

**卸载本模块后核心必须仍能正常发布**（R6.4）。这是硬约束，已经真做过一次卸载验证：
``infohub.rule`` 模型与表消失，核心的默认发布、人工标黑、三轴解析全部照常工作。

规则求值
========

按 ``sequence`` 升序。条件由两部分组成，**都满足**才算命中：

* ``condition_domain`` —— 对 ``infohub.item`` 的 Odoo domain，留空表示不限
* ``keyword_regex`` —— 正则（忽略大小写），可选匹配范围为标题 / 正文 / 两者，
  留空表示不限

动作分两类：

=============  ==========  ==================================================
动作           类型        行为
=============  ==========  ==================================================
``publish``    终结型      定为已发布，该条目不再过后续规则
``reject``     终结型      定为已拒绝，该条目不再过后续规则
``tag``        标注型      打标签后继续过后续规则
``score``      标注型      加减评分后继续
``topic``      标注型      指派学科后继续，可选同时设为主学科
=============  ==========  ==================================================

标注型规则勾上 ``stop_after`` 可以中断后续求值，但状态仍交回核心决定。

正则的两个防护
==============

**保存时校验**：``re.compile`` 失败直接拒绝保存，不让坏正则跑到采集流水线里才炸。
``condition_domain`` 同样在保存时 ``safe_eval`` + ``Domain.validate``。

**限制被匹配文本的长度**：Python 的 ``re`` 没有超时机制，一个写得不好的正则（嵌套
量词等）在长文本上可能指数级回溯，把 worker 卡死。所以只对正文的前 100000 个字符做
匹配。**这不能根治 ReDoS**，但把最坏情况的输入规模压到了可控范围。写规则时仍应避免
嵌套量词。

写规则的建议流程
================

1. 建规则但先不启用
2. 点「试运行」—— 在最近 200 条条目上试跑，只报告命中数，不改任何数据
3. 点「查看命中的条目」确认没有误伤
4. 启用

只取样本而不全量扫，是因为正则匹配在 Python 里做，全量会很慢。

权限
====

``infohub.group_moderator`` 可增删改规则，``infohub.group_user`` 只读。规则会改变
portal 读者能看到什么，所以不开放给普通内部用户。
