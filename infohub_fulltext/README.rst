====================
InfoHub 正文提取
====================

很多 RSS 只在 ``<description>`` 里给一两句摘要，读者点进详情页看不到内容。本模块为
这类条目按需抓取原文页面，用 trafilatura 剥掉导航、广告、推荐位，只保留正文，净化后
回写到条目上。

工作方式
========

挂一个 ``usage = 'enricher'`` 的 component。采集流水线在条目落库后派发独立的
queue_job 任务来跑增强，不阻塞采集（R10.2）——正文提取要为每个条目额外发一次 HTTP
请求，同步做会让抓取轮次慢一个数量级。

只在需要时抓取
--------------

三个条件同时满足才会去抓：

* 源上 ``fulltext_enabled`` 为真（默认真：装了本模块通常就是想用它）
* 条目有 ``url``
* 现有 ``content_text`` 长度小于源上的 ``fulltext_min_length``（默认 500）

处理结果记在 ``fulltext_state`` 上（``pending`` / ``done`` / ``skipped`` /
``failed``），**已成功或已失败的条目不会反复重试**。来源站改版后，管理员可以在条目
表单上点「重新提取正文」把状态重置并重跑。

单次任务最多处理 ``BATCH_LIMIT``（50）条，剩下的留给下一轮，避免一个任务跑太久被
worker 超时杀掉。

失败的几种情形
==============

都会写进 ``fulltext_error`` 并把状态置为 ``failed``，不中断整批增强：

==========================  ================================================
情形                        说明
==========================  ================================================
URL 未通过安全校验          指向内网或协议不允许。这是配置/数据问题，不是临时故障
网络错误                    超时、连接失败、HTTP 错误码
未识别出正文                trafilatura 返回空。页面结构过于异常
正文过短（< 200 字符）      多半拿到了付费墙、cookie 同意页或反爬页面
==========================  ================================================

出网约束
========

抓原文一律走核心的 ``infohub.http`` component，因此自动继承 SSRF 防护、超时、响应
体积上限——**不要绕过它直接用 requests**。两次请求之间按源上的
``min_request_interval`` 休眠：连续抓原文比抓 feed 更容易触发来源站封禁。

净化不外包
==========

trafilatura 本身会去掉脚本，但提取结果仍然过一遍 ``html_sanitize``。安全性不外包给
第三方库是本项目的一条底线（N4）——正文会渲染到 website 公开页面。

字段为什么加在 ``infohub.item`` 上
==================================

``fulltext_state`` / ``fulltext_error`` / ``fulltext_length`` 直接加在核心条目表上，
而不是像论文那样放介质载荷表（ADR-005）。理由：载荷表是给**介质特有的结构化数据**
用的，而正文提取是**横切的处理状态**，与介质无关（文章、论文、社交内容都可能需要）。
为一个处理状态单开一张表，反而会让"哪些条目待处理"的查询变成联表。

依赖
====

``trafilatura``。本项目的容器镜像 ``odoo:19.0`` 已自带（2.2.0），无需额外安装。

测试
====

见 ``.kiro/specs/infohub/stage4_test.py`` 第 7–8 节：候选筛选、成功回写、四类失败
分支、失败后不重试、手工重试。用注入的假 HTTP 响应，不联网。
