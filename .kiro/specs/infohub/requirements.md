# InfoHub 需求文档

## 1. 背景与目标

构建一组 Odoo 19 addon，把分散在 RSS 新闻、博客、学术论文、社交平台上的在线信息汇集成统一的、可按学科/标签订阅的信息流。内部用户负责源管理与内容审核，portal 用户在 website 端按自己的关注面阅读。

核心设计目标：**新增一个信息来源的成本应尽可能接近于"加一条数据记录"，而不是"写一个模块"。**

## 2. 角色

| 角色 | 组 | 场景 |
|---|---|---|
| 读者 | `infohub.group_reader` (portal) | 在 website 端管理自己的订阅、浏览时间线、标记已读/收藏 |
| 内部用户 | `infohub.group_user` | 后台查看条目、源、抓取日志 |
| 审核员 | `infohub.group_moderator` | 人工标黑、调整条目状态、维护过滤规则 |
| 管理员 | `infohub.group_manager` | 管理源、凭证、学科词表 |

## 3. 功能需求

### R1 信息源管理（核心）

- R1.1 管理员可创建、编辑、停用信息源；源由 `medium`（介质）、`transport`（传输）、`provider`（来源）三个维度组合定义。
- R1.2 系统应拒绝无实现支撑的三维组合，并给出明确提示（提示应指向可能缺失的模块）。
- R1.3 各渠道模块可提供"源预设"（preset）数据记录，管理员建源时选择预设即自动填好三个维度与端点信息。
- R1.4 每个源可配置轮询周期；系统按周期自动抓取。
- R1.5 每个源可配置默认学科与默认标签，自动继承给其产出的条目。
- R1.6 源连续抓取失败达到阈值后应自动停用并通知管理员。
- R1.7 需要认证的源，其凭证独立存储，仅管理员可读。

### R2 采集与归一化（核心）

- R2.1 抓取必须是增量的：系统为每个源保存游标状态（ETag / Last-Modified / since_id / 最后发布时间等，形态因源而异）。
- R2.2 抓取必须异步执行，单个源的失败或超时不得影响其他源。
- R2.3 同一个源在上一轮抓取未完成时不得被重复入队。
- R2.4 每次抓取应产生一条运行日志，记录起止时间、发现条目数、新建数、跳过数、错误堆栈。
- R2.5 系统应保存来源的原始报文，以便解析规则变更后可在不重新联网的前提下重跑归一化。
- R2.6 归一化后的条目应包含统一的核心字段（标题、URL、作者、摘要、正文、发布时间、语言）。
- R2.7 介质特有的结构化数据存放在该介质自己的载荷表中，不占用核心条目表。
- R2.8 系统应能遵守来源方施加的请求速率限制，且该限制必须是**全局**的：跨 worker、跨同一来源方的多个源记录共同生效。

### R3 去重（核心 + 介质层）

- R3.1 同源去重：同一源内相同外部标识的条目不得重复入库。
- R3.2 跨源去重：同一内容经不同源进入时应收敛为一条。
- R3.3 去重身份的计算规则由介质决定（论文用归一化 DOI，新闻用 GUID/URL 规范化），核心不硬编码。

### R4 学科词表与标签（核心）

- R4.1 学科（topic）为层级受控词表，订阅某学科应自动包含其全部子学科。
- R4.2 标签（tag）为扁平自由词表，可由规则引擎、LLM 或人工产生。
- R4.3 系统提供"外部分类码 → 学科"映射表，各渠道模块以数据形式带入自己的映射（arXiv 分类码、MeSH 等）。
- R4.4 学科树初始数据采用 arXiv 分类体系作为种子。
- R4.5 新增学科领域应只需增加映射数据，不需修改代码。

### R5 审核与标黑（核心）

- R5.1 条目状态：`fetched` → `published` / `rejected` / `blocked`。仅 `published` 对 portal 可见。
- R5.2 默认行为为自动发布；核心提供审核钩子供过滤模块介入。
- R5.3 审核员可对单条条目人工标黑，已发布的条目应立即从 portal 撤下。
- R5.4 审核员可按来源、域名、关键词、作者建立黑名单；此类黑名单对新进条目前瞻生效。
- R5.5 前瞻性黑名单应支持一次性回溯扫描，把历史条目一并标黑。
- R5.6 黑名单类型应可被后续模块扩展。

### R6 规则引擎（`infohub_filter`）

- R6.1 管理员可定义有序的过滤规则，条件支持条目 domain 与标题/正文正则。
- R6.2 规则动作支持：发布、拒绝、打标签、加减评分、指派学科。
- R6.3 规则可配置命中后是否终止后续规则。
- R6.4 该模块缺失时，核心必须仍能正常自动发布。

### R7 订阅（核心）

- R7.1 每个读者可自主创建订阅；订阅目标可以是源、学科或标签。
- R7.2 订阅目标类型应可被后续模块扩展（如按作者、按期刊、按关键词订阅）。
- R7.3 读者可设置屏蔽标签与关注语言，作用于其全部时间线。
- R7.4 读者的时间线为其所有订阅的并集，减去屏蔽项。
- R7.5 订阅变更应立即对时间线生效，不需回溯重算。
- R7.6 读者只能读写自己的订阅与阅读状态。

### R8 阅读状态（核心）

- R8.1 已读、收藏、隐藏均为"每用户每条目"的状态，互不影响。
- R8.2 阅读状态的存储量应与实际交互量成正比，而非与「用户数 × 条目数」成正比。
- R8.3 系统应能给出每个订阅的未读数量。

### R9 Website 阅读（`infohub_website`）

- R9.1 读者在 website 端查看个人时间线，支持按学科、标签、未读状态筛选与分页。
- R9.2 条目详情页展示正文与原文链接；打开即记为已读。
- R9.3 读者在 website 端管理自己的订阅。
- R9.4 后台标准视图保留，供内部用户做源管理、词表维护与抓取排错。
- R9.5 portal 读者通过**自助注册**开通（`auth_signup`）；需邮箱验证，并对注册滥用有基本防护。
- R9.6 新注册读者应获得一组默认订阅，避免首次进入时时间线为空。

### R10 正文补全（`infohub_fulltext`）

- R10.1 对仅提供摘要的条目，按需抓取原文并提取正文主体。
- R10.2 正文提取应作为独立的异步任务，不阻塞采集。

### R11 论文介质（`infohub_paper`）

- R11.1 论文条目附加结构化字段：DOI、摘要、作者、期刊、卷/期/页、发表阶段、引用数、PDF 链接。
- R11.2 **只保存 PDF 的 URL，不下载、不存储 PDF 文件。**
- R11.3 DOI 应做归一化后再用于去重。
- R11.4 作者与期刊为独立模型，可跨条目复用。

### R12 渠道模块

- R12.1 `infohub_rss`：RSS/Atom 采集，覆盖新闻与博客；新增常规 RSS 源不需要写代码。
- R12.2 `infohub_web`：无 RSS 站点的选择器抓取；常规站点通过"选择器配置"记录接入，不需要写代码。
- R12.3 `infohub_arxiv`：arXiv 采集与学科码映射。
- R12.4 `infohub_pubmed`（未来）：生物医学与 MeSH 映射。
- R12.5 `infohub_social` / `infohub_twitter`（未来）：社交介质与 X API v2。

### R13 分发与增强（后续）

- R13.1 `infohub_digest`：按订阅周期推送摘要邮件。
- R13.2 `infohub_llm`：桥接既有 `llm` 模块，提供摘要、翻译、零样本学科分类。

## 4. 非功能需求

### 性能
- N1 条目规模按十万至百万级设计；时间线查询与未读计数必须走索引，不得依赖 m2m 联表的记录规则。
- N2 采集、正文提取、LLM 处理分别为独立任务，互不阻塞。

### 安全
- N3 源 URL 由用户输入且由服务端发起请求，必须限制协议为 http/https，并拦截私有网段、环回地址与链路本地地址（防 SSRF）。
- N4 第三方 HTML 正文将渲染到 website 公开页面，必须经过净化，剥离脚本、内联事件与内嵌框架（防 XSS）。
- N5 所有出网请求必须设置超时与响应体积上限。
- N6 凭证不得对 portal 用户或普通内部用户可读。
- N7 portal 用户对订阅与阅读状态的访问必须由记录规则限定在本人范围内。

### 可扩展性
- N8 新增介质、传输、来源三类扩展应各自独立，互不需要修改对方或核心。
- N9 一个渠道模块原则上只在一个维度上贡献实现；确有必要跨维度时须在模块文档中说明。
- N10 来源数量增长时，模块数量应保持次线性增长。

## 5. 范围外

- 不下载或存储 PDF 文件（仅存 URL）。
- 不桥接 `knowledge_base`。
- **不做站内通知**；对外触达只有 `infohub_digest` 的摘要邮件。
- 本期不实现 Twitter/X 采集（访问权限待定），但保留 `infohub_social` 介质层的设计位置。
- 不做自定义 OWL 阅读器；后台使用 Odoo 标准视图，前端使用 QWeb 模板。
